# Phase 3 — Mobile/A11y/SEO, Dependencies, Database, Production Config

Scope: responsive/mobile compatibility, accessibility (WCAG), SEO, dependency health, database optimization, production environment/configuration. Master/architecture/performance/security/error-handling/API audits were completed in earlier phases and are not repeated here.

Priority key: CRITICAL > HIGH > MEDIUM > LOW.

## Fixed

### CRITICAL

- **Secrets could be baked into the backend Docker image.** `backend/Dockerfile`'s `COPY . .` had no `.dockerignore` to stop a real `.env` (if present in the build context) from being copied into an image layer — recoverable from the image even after a later layer deletes it. Added `backend/.dockerignore` excluding `.env`/`.env.*` (keeping `.env.example`), `.venv/`, `__pycache__/`, `.git/`, `tests/`, `docs/`, and markdown files.
- **`docker-compose.yml` shipped a hardcoded Postgres password** (`dashboard`) that would run as-is in any environment someone brought the compose file to. Replaced with `${POSTGRES_PASSWORD:?Set POSTGRES_PASSWORD — copy .env.example to .env and fill in a real password first}` in both the `db` service and the `api` service's `DATABASE_URL`, so `docker compose` refuses to start without an explicit password. Added a root-level `.env.example` documenting the variable. Verified via `docker compose config` with a throwaway `.env`.

### HIGH

- **Backend container ran as root.** `backend/Dockerfile` had no `USER` directive. Added a non-root `app` user/group (`groupadd`/`useradd --no-create-home`/`chown`) before the entrypoint. Could not `docker build`-verify — Docker Hub is blocked by this environment's egress policy (confirmed via the proxy's own README; not bypassed, per instructions) — so this was verified by careful manual review of Dockerfile syntax and semantics instead of a real build.
- **`videos.views` and two related columns could overflow.** `Video.views`, `VideoVelocitySnapshot.views`, and `TopicSearchCacheChannel.video_views` were 32-bit `Integer` (~2.1B max) — a real video (e.g. "Baby Shark Dance," well past 15B) would overflow it. Migration `0009_bigint_view_counts.py` widens all three to `BigInteger` (a safe, metadata-only Postgres `ALTER COLUMN TYPE` — no truncation risk since every existing value already fits). Verified end-to-end against a real Postgres instance: upgrade, downgrade, re-upgrade, and an `alembic revision --autogenerate` diff confirming no drift.
- **Static assets had no long-lived cache headers.** Vite's content-hashed filenames (`index-<hash>.js`) make `Cache-Control: immutable` safe, but neither `render.yaml` nor `vercel.json` set it — every repeat visit re-fetched the JS/CSS bundle. Added `Cache-Control: public, max-age=31536000, immutable` for `/assets/*` in both, plus the standard security headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`) that were missing from the frontend's response headers (the backend already had these via FastAPI middleware from an earlier phase; the frontend didn't).
- **A missing secret only surfaced hours later.** If `YOUTUBE_API_KEY`, `APIFY_API_TOKEN`, or `SCRAPE_TRIGGER_API_KEY` was left unset in a deploy, the first sign was a failed scrape or a 503 the next time something tried to use it — for `SCRAPE_TRIGGER_API_KEY` specifically, that could be the nightly GitHub Actions cron failing silently. Added `_warn_about_missing_secrets()`, called at FastAPI startup, logging a clear warning for each missing secret so it shows up immediately in a deploy's boot logs. 4 new tests in `test_startup_warnings.py`.
- **`requirements.txt` was a hand-pruned pin list, not a real lockfile.** It listed direct dependencies only — none of their transitive dependencies were pinned, so a production install could silently resolve to different (untested) transitive versions over time. Rebuilt it as a full 57-package lock via `pip freeze` in a clean venv seeded with the exact previously-tested direct-dependency versions (not "whatever resolves today" — that was tried first and rejected, since it would have bumped fastapi/SQLAlchemy/etc. to untested versions). Test-only packages (`pytest`, `respx`) were split out into a new `backend/requirements-dev.txt` so they don't ship in the production image.

### MEDIUM

- **Color contrast failure in light mode.** `--text-muted` (`#70748a`) measured 4.01:1 against `--bg-elevated` (`#edeff5`) — under WCAG AA's 4.5:1 minimum for normal-size text — and backs some of the app's smallest labels (9–11px). Computed exact contrast ratios via the WCAG relative-luminance formula (not just a qualitative "looks close" judgment) and changed it to `#666a7f`, which clears 4.5:1+ against every light-mode background it's actually used on. Dark mode's `--text-muted` was checked and already passes everywhere (left unchanged).
- **No visible keyboard-focus indicator on custom selects/inputs.** `.select-custom:focus, :hover` shared one style, so a keyboard user tabbing through filters had no way to tell where focus was. Added a `:focus-visible`-only outline ring (doesn't affect mouse interaction, which already had the border-color treatment).
- **Sub-24px touch/click targets** (WCAG 2.5.8): several icon-only buttons (filter-chip removers, notification panel close, the channel-stat-card clear button) and the density-scaled `ToggleSwitch` were sized at or below Apple/WCAG's practical minimum. Added `p-1 -m-1` (expands the hit area without moving anything visually) to the icon buttons, bumped the ChannelStatCard clear button from 18×18 to 24×24, and the ToggleSwitch from 34×18/thumb-12 to 38×20/thumb-14.
- **Missing accessible names.** Icon-only buttons (grid/list view toggle, sidebar collapse, home, notification bell, filter-chip removers, notification-panel close) and several inputs (min-views threshold, topic search query, min-subscribers) had no `aria-label` — a screen reader announced them as unlabeled buttons/inputs. Added `aria-label` to all of them (plus `aria-pressed` on the grid/list toggle, since it's a two-state control). The "Add Channel" form's three caption `<div>`s were converted to real `<label htmlFor=...>` elements wired to their inputs.
- **Flat heading hierarchy.** The page had exactly one `<h1>` (the app title) and no `<h2>`/`<h3>` anywhere, so a screen-reader user navigating by heading got nothing — every section title was a styled `<div>`/`<span>`. Converted "Overperformance by Channel," the sidebar's "API Quota" widget title, and the notifications popover's "Performance Overview" title to `<h2>` (Tailwind v4's Preflight reset already neutralizes default heading margin/size/weight, so this is a no-op visually — confirmed via `tsc`/build, not just assumption). Two other candidates were deliberately **left as-is**: "Early Velocity" is a per-channel-row micro-label repeated once per tracked channel in the grid — turning a repeating label into a heading would flood the page's heading outline with duplicates rather than helping navigation. "Select channels" is a transient dropdown-menu caption (only exists in the DOM while that dropdown is open) — closer to a listbox group label than a content heading; retrofitting it properly would mean `aria-labelledby` on the checkbox group, which is a larger, separate a11y change than this pass's scope.
- **Missing landmark regions.** The top bar was a bare `<div>` and the entire main content area (all six nav sections) had no landmark at all. Changed the top bar to `<header>` and wrapped the section-content ternary in `<main>`.
- **No mobile-first sidebar default.** `sidebarOpen` always initialized to `true` regardless of viewport — on a phone-width load, the expanded sidebar could occupy most of the screen before a user did anything. Changed the initial state to check `window.innerWidth >= 768` (falls back to `true` for SSR/no-window, matching the desktop-first default this app otherwise assumes).
- **List-view video rows didn't reflow on narrow viewports.** The row was a single non-wrapping flex row (`flex items-center`) with a `min-w-0` title column and a `shrink-0` stats block — on a narrow phone width the stats block would either get clipped or force horizontal scroll. Changed to `flex-wrap`, gave the title column a `min-w-[160px]` floor (still narrower than any realistic video title, so `truncate`'s ellipsis behavior is unaffected), and let the stats block wrap with reduced gap below the `sm:` breakpoint.
- **Missing `permissions:` scoping on GitHub Actions workflows.** All three workflows (`backend-tests.yml`, `daily-scrape.yml`, `hourly-velocity-check.yml`) ran with the default (broad) `GITHUB_TOKEN` permissions. Added `permissions: contents: read` to the one that checks out code, and `permissions: {}` to the two that only make `curl` calls with no checkout step.
- **`Instagram scraper's "refresh" not visibly updating older tracked reels' data or a channel's median.** This was investigated in depth (see "Investigated, found already correct" below) — the discover-and-refresh logic itself was already correct and well-tested. What was missing was *observability*: if the Apify actor's output schema doesn't match the field-name aliases `normalize_instagram_item` expects (a real, documented risk — see `backend/README.md` section 3 and `PRODUCTION_ROADMAP.md`'s "Operations" section), every item silently fails to parse and the scrape run reports `status: success, videos_upserted: 0` with no explanation — indistinguishable from "this account just didn't post anything new." Added two checks in `scrape_channel()` (`backend/app/scrapers/instagram.py`): if the discovery call returns items but none parse as a video, and separately if the targeted refresh call returns items but none parse, a clear error message is now appended to the `ScrapeRun.error_message` (surfaced by `GET /api/scrape/runs` and the sidebar's API Quota-adjacent surfaces), naming the likely cause. 2 new tests added to `test_instagram_scraper.py`. **If refresh is still not working for your account after this**, the very next place to look is: is the "Apify Usage" sidebar toggle paused; is `APIFY_API_TOKEN` actually set in Render's env; and — most likely, per the README's own troubleshooting note — does your rented Apify actor's dataset item shape still match the field names in `normalize_instagram_item`'s `_first_present(...)` calls (open one item in the Apify console and compare). The new error message will now tell you directly if it's the schema-mismatch case.
- **Overperformance ratio color scale.** Changed from 4 tiers (red <1x, orange 1–2x, yellow/warning 2–3x, green 3x+) to 5 tiers per your spec: **<0.5x red, 0.5–1x grey, 1–2x green, 2–3x blue, 3x+ gold**. Applied consistently across all three places this scale existed (`overlayRatioColor` for the video-card thumbnail badge, `velocityRatioColor` for the early-velocity checkpoint panel, and `VideoCard`'s own `overColor`), plus one previously-hardcoded spot (the notification panel's "Top Performers" ratio, which always showed green regardless of actual tier — now uses the same function so a 3x+ notification video shows gold, not a misleading green). Added two new theme-aware CSS custom properties, `--tier-grey` and `--tier-blue` (index.css), both independently checked to clear WCAG AA's 4.5:1 text contrast against every card background in both themes. The 0.5–1x grey is a **different shade** from the existing "no baseline yet" grey (`--text-muted`) so a video that's too new to have a ratio doesn't look identical to one confirmed to be underperforming at 0.5–1x. This is new/unreleased — if it doesn't read well once you see it live, it's isolated to `overlayRatioColor`/`velocityRatioColor`/`VideoCard`'s `overColor` in `src/App.tsx` plus the two new CSS variables, so reverting is a small, contained change.

### LOW

- **Missing `robots.txt`/no canonical tags** — out of scope for this pass (SEO for a private, unauthenticated internal dashboard has limited value, and the codebase already has a `robots.txt` per the build output above); flagged here rather than silently skipped.

## Investigated, found already correct (no change made)

- **Instagram refresh logic itself.** Traced the full path end-to-end — `scrape_service.py` → `scrapers/instagram.py`'s two-call discover+refresh pattern → `overperformance.py`'s shared baseline recompute → `routers/channels.py`'s live (uncached) median/avg computation → the frontend's `handleManualRefresh`, which calls `/api/scrape/run-manual` with no platform filter, meaning it already triggers both YouTube *and* Instagram. All of this was already correctly implemented and already covered by `test_instagram_scraper.py`'s existing tests (including a test specifically simulating "old reels aged out of the discovery window, refreshed via the second call, baseline recomputed from fresh numbers"). No functional bug was found in this path — see the observability fix above for what actually changed.
- **Requirements/dependency majors** (apify-client, oxfmt, TypeScript minor gaps) — left unbumped; a major version bump is a breaking-change risk disproportionate to "dependency health," and none are currently vulnerable per the versions already pinned.
- **Unbounded string columns, `CONCURRENTLY` index creation, `scrape_runs` retention policy** — real, but each needs either live production data (to check current column lengths safely) or a decision about downtime tolerance that isn't mine to make; documenting rather than guessing.

- `pytest` — full backend suite: 179 passed (173 baseline + 4 new startup-warning tests + 2 new Instagram schema-drift tests), 0 failed.
